# Модуль C. Доставка помощи, рекламная готовность и измерение

Дата: 13 ноября 2026 года. Исследовательская база: `DanilaH/arrows`, `ad4bc416aa26e6bbc257875675a428c281564ff9`, версия 0.19.1 / Android code 31. Перед реализацией сверить модуль с актуальной рабочей веткой и сохранить более свежие изменения. Этот документ описывает требования к будущей реализации; перечисленные новые события, кэш rewarded и получение резервной помощи ещё не считаются реализованными.

## C.0. Цель и границы

Игрок должен получать именно ту помощь, которую выбрал, а команда — отличать видимое предложение, рекламный показ, сохранённое право и фактическое использование помощи. После этой работы можно сравнивать коммерческие варианты по общему результату, а не только по количеству запросов рекламы.

Первая поставка: C + улучшенный выбор существующей одиночной подсказки A1 + общая подача F; ограниченный каскад A2 доставляется как изолированный кандидат. A1 является базовым поведением кандидатов, а A2 меняет дополнительную силу награды; это различие должно быть видно в конфигурации и данных. Ручной маршрут, продолжение с подсказкой и режим цели идут следующими отдельными изменениями. Не включать одновременно несколько новых коммерческих условий для одной аналитической группы.

Не создавать новый рекламный фреймворк, универсальный кошелёк, удалённую конфигурационную платформу или внешний сервис экспериментов ради этого пакета. Использовать существующие точки расширения. Runtime mini-games-kit остаётся на `a9325265e87583a4872cf6a158e1e881a0d7508e`; изменение пина допустимо только при подтверждённой необходимости конкретного общего API и отдельной проверке совместимости.

### Что уже есть и сохраняется

- TS и Android читают один точный JSON-контракт аналитики. Лимит транспорта — 32 незавершённых вызова. SDK acceptance уже отделён от доставки в кабинет. Этот слой расширяется; заново устранять предполагаемую рассинхронизацию allowlist из другого проекта не требуется [C1].
- Native-журнал хранит earned receipts через AtomicFile/readback, поддерживает очередь и подтверждение конкретного ID. Эффект и дедупликация применяются единственным авторитетным writer игровых сохранений. SDK earned является источником права на награду [C2, C3].
- Один free continue на весь сохранённый профиль; все продолжения возвращают три жизни. Ошибки остаются. Использование Hint само по себе не лишает безошибочного результата [C2].
- Обычная подсказка появляется после трёх активных секунд без успешного удаления и сохраняет цель до её удаления. Три секунды не являются сроком действия полученной помощи [C4].
- Межуровневый показ разрешается только при явном Next после нового подтверждённого результата, `wins >= 6`, двух новых уникальных победах с предыдущего запроса и 150 секундах допустимой активной игры. Время рекламы, фон и блокирующие экраны не превращаются в игровое активное время. Политика обновляется уже при запросе, включая неудачный [C5].
- `.playtest` имеет отдельный package ID и прогресс, принудительные test ads и пустой analytics key. Это предназначенная пользователю тестовая сборка [C6].

## C.1. Стабильный договор о награде до показа рекламы

### Зачем

Текущий receipt schema 1 содержит `id`, `attempt`, `mode`, `placement: hint|lives`. Он не описывает каскад, маршрут, выбранный план, размер эффекта или вариант эксперимента. Определять эти свойства по текущему feature flag в момент позднего earned запрещено: игрок мог уже выбрать другой продукт, перезапустить попытку или обновить приложение.

### Требуемое поведение

1. До native show сохранять описание принятого запроса через существующий авторитетный writer: `requestId`, владельца попытки, версию/идентичность контента, `effectKind`, `effectVersion`, идентификатор коммерческого варианта и неизменяемое обещание награды. Для A2/A3 включить данные плана, необходимые для независимого восстановления и проверки, по контракту core-модуля.
2. При недоступной/неопределённой записи show не вызывается. Нельзя сначала получить earned, а затем впервые пытаться вспомнить обещанное предложение.
3. Native show принимает тот же request ID. Прогретый рекламный объект до этого момента не имеет владельца attempt или награды. Earned связывается с описанием только по request ID; его нельзя переназначить последнему активному экрану.
4. Новый протокол должен отличать новый запрос без найденного описания от настоящего legacy receipt. Допустима версионированная receipt/request-схема с версией intent или ссылкой/контрольным отпечатком описания. Конкретный формат выбирает агент, но различение проверяется тестом. Если все новые receipts оставить неотличимыми от schema 1, безопасно реализовать legacy fallback не получится.
5. Старые schema 1 receipts продолжают выдавать исходную одиночную подсказку либо три жизни. Они не превращаются в каскад/маршрут после обновления. Новое earned-право без достоверного описания сохраняется отдельно для восстановления и диагностики, а не угадывается и не удаляется.
6. Один earned создаёт ровно одно право. Запись права и дедупликация ID — одна транзакция; native acknowledge конкретного ID происходит только после подтверждённой записи. Одно право на каскад/маршрут покрывает весь обещанный эффект без новых рекламных запросов за его шаги.
7. Длительность анимации не управляет правом на помощь. Применение игрового эффекта, сохранение результата и списание права должны быть атомарны по правилам core; звук/вибрация/подсветка следуют за ними.
8. Kill switch прекращает новые предложения кандидата, но не переписывает уже выданную помощь. Смена варианта не меняет старый effectKind, amount, план или принадлежность. Для остановленного вида должен сохраняться совместимый обработчик уже выданных прав.

Данные описания хранятся минимально достаточным образом. Очистка завершённых записей не должна делать повторный receipt новым, а поздний callback — неидентифицируемым. Не вводить бесконечный in-memory журнал или копию полного поля в каждом аналитическом событии.

## C.2. Предзагрузка rewarded и правдивая готовность

### Фактическая база

Interstitial уже предзагружается. Rewarded загружается после явного tap и имеет таймаут 15 секунд до show invocation и retry backoff 30 секунд. `status().rewarded` означает конфигурационную доступность, не наличие готового видео. Эти свойства подтверждены native-кодом [C3].

### Новый контракт

- Разделить configured/enabled, initializing, loading, ready, showing, backoff и unavailable. Имена API могут отличаться; интерфейс и аналитика должны различать эти состояния.
- В foreground допустим один кэшированный rewarded object и один загрузочный запрос. Предзагрузка не блокирует первый кадр, не ставит игровой ad blocker, не расходует полученную помощь, не отмечает offer как принятый и не сдвигает interstitial cadence.
- Запускать прогрев по ограниченному событию спроса после готовности приложения/входа в подходящую игру, а не на каждом render. Не повторять запросы фоновым бесконечным циклом. После ошибки использовать существующий начальный backoff 30 секунд; новый запрос допускается только при актуальном foreground-спросе.
- Для кэша нужны loadedAt/expiry и generation. Начальный app-level TTL допустимо выбрать консервативным, например пять минут; это собственная настройка приложения, не заявление о сроке жизни SDK-объекта. Если SDK имеет более короткое ограничение, соблюдать его. Значение и основание записать в решениях проекта.
- Ready означает: объект загружен, не использован, не просрочен, принадлежит текущему поколению loader. Возможность показа дополнительно зависит от foreground, фокуса Activity, отсутствия другой ad session и безопасного writer наград.
- Объект привязывается к конкретным requestId/attempt/placement только после явного согласия игрока и сохранения описания запроса. Готовность кэша не должна сама вызывать show.
- При ready явный запрос использует кэш. При loading доступен понятный отменяемый экран ожидания; он не меняет обещание помощи. При unavailable — краткое объяснение, возврат к игре и нормальная возможность попробовать позже. «Готово» нельзя показывать по одному configured flag.
- Если игрок отменил ожидание, вышел в фон или сменился владелец запроса, поздний onLoaded не вызывает show. Callback старого поколения не способен заменить текущий кэш или завершить другую сессию.
- После использования/ошибки показа объект снимается с кэша и listener очищается. Новый прогрев возможен после завершения текущей сессии и восстановления foreground, с соблюдением бюджета.
- Отмена до invocation не выдумывает закрытие уже открытого SDK-экрана. Существующее независимое владение ad blocker и foreground blocker сохраняется.

Не повышать рекламную частоту одновременно с этой работой. Сравнивать прежде всего задержку от выбора помощи до запуска показа, долю отказов/отмен ожидания и доставку награды.

## C.3. Получение сохранённой помощи

В базе `reservedRewards` сохраняет earned права от завершённых/сменившихся попыток. Отдельного пользовательского claim-пути в `src` нет. Это сохранённое право, но пока не доступная игроку помощь. Частота таких случаев по живым данным неизвестна [C2, C4].

### Как использовать резерв

1. Существующее earned право должно быть заметно там, где игрок получает помощь: например «Есть сохранённая подсказка — использовать». Новая валюта, общий магазин и отдельный экран инвентаря не нужны.
2. Получение требует явного действия пользователя и подходящей попытки. Для самостоятельного hint/каскада/маршрута это незавершённая попытка с положительным числом жизней и свободным слотом помощи; для lives — незавершённая попытка с нулём жизней. Для целого A4 bundle применимость проверяется по исходному состоянию: незавершённая целевая попытка с нулём жизней. Жизни и помощь рассчитываются в одной кандидатной транзакции: восстановление до трёх, затем A1 либо резерв его компонента при занятом слоте по TASK.md, раздел 4.2. Положительные жизни не являются предварительным условием claim целого bundle. Отдельный оставшийся A1-компонент требует обычных условий самостоятельной помощи.
3. Перед новым рекламным предложением показывать доступный совместимый резерв. Нельзя предлагать ещё один просмотр за ту же помощь, когда готовое сохранённое право может быть использовано здесь.
4. Claim — отдельная атомарная операция: убрать из доступного резерва конкретное применённое право, привязать его к проверенной новой попытке и сохранить статус claimed. Для составного права переходы учитываются по компонентам: применение жизней остаётся в истории, а незатребованный A1 остаётся доступным в резерве; состояние всего entitlement не скрывает и не расходует оставшийся компонент. Вызов обычного `commitReward` с тем же ID не подходит: такой ID уже присутствует в receipt dedup ledger.
5. При claim A2/A3 можно построить подходящий план для новой попытки по правилам core, сохранив тип, версию/семантику и размер выданной помощи. Нельзя автоматически заменить одиночный Hint более сильным продуктом или повторно взимать видео.
6. В аналитике сохраняются исходный request/receipt ID и исходный owner; отдельно записывается фактический attempt получения/использования. История выдачи не переписывается.
7. Двойной tap, восстановление после crash и повторная доставка native receipt не создают второе право. При uncertain save claim остаётся неуспешным/ожидающим подтверждения; UI не обещает выдачу до авторитетного результата.
8. Уже активная помощь не заменяется новым поздним receipt. Любое новое самостоятельное право при занятом слоте помещается в резерв. Для A4, обещавшего новый A1, при актуальном owner на нуле жизней применяются жизни и резервируется только занятый компонент помощи по TASK.md, раздел 4.2. Это покрывает окно, которое обычное скрытие второй кнопки Hint не защищает.
9. Нельзя удалять самые старые неполученные права ради ограничения массива. Ограничивать загрузку, обработку, отображение и при необходимости возможность новых рекламных запросов до восстановления хранилища. Earned-права не теряются из-за лимита UI.

Перезапуск попытки обрабатывает неиспользованную помощь по контракту core. Полный сброс пользовательских данных/переустановка не добавляются как новая функция этого ТЗ и не используются как способ проверить миграцию; существующий прогресс пользователя не удалять.

## C.4. Воронка и события

Расширять общий TS/native JSON-контракт вместе с отправителями. Существующие имена нельзя молча переопределить: `hint_applied` в базе означает сохранённую подсветку, а не совершённое по ней действие. Можно сохранить это имя с прежней семантикой и добавить новые события, либо явно версионировать новую схему и отчёт.

### Минимальная измеримая цепочка

| Факт | Когда фиксировать | Основная связь |
| --- | --- | --- |
| Вариант назначен | Один раз при включении в подходящую группу; назначение стабильно | assignment ID, experiment ID/version, variant, install/cohort |
| Предложение видно | В foreground оно действительно видно и не закрыто другим экраном | offer ID, attempt, effect kind/version, variant, eligibility/readiness |
| Выбор предложения | Явный tap/отказ/выход/Restart из соответствующего предложения | offer ID, choice; request ID только если запрос принят |
| Начался/готов прогрев | Настоящие события loader | preload ID/generation, формат, elapsed, outcome; без выдуманного attempt owner |
| Запрос/show/impression/result | Реальные события SDK/сессии | request ID, формат, placement, attempt, outcome, кэш/холодная загрузка |
| Earned получен | SDK callback, отдельно от его долговечности | receipt/request ID, исходный owner |
| Право сохранено либо зарезервировано | Подтверждена транзакция save | entitlement ID, receipt ID, effect/version, destination/status |
| Резерв получен | Подтверждён atomic claim | тот же entitlement/receipt ID, source owner, target attempt |
| Помощь использована | Реально применён игровой результат | entitlement ID, attempt, causal action ID, тип и размер эффекта |
| Результат продолжения | Первый успешный ручной ход / повторная потеря жизней / выход / завершение | entitlement ID продолжения, attempt, active elapsed, outcome |

Идентификаторы и данные сохраняются без персональных сведений или полной геометрии поля в событиях. Не требуется повторять все поля на каждом native событии: допустимо достоверное соединение по request ID с описанием запроса. Для всех обязательных joins должен существовать воспроизводимый пример.

### Правила подсчёта

- Offer visibility считается по эпизоду видимости, а не при каждом `sync()` или кадре. Повторное открытие создаёт новый эпизод с тем же логическим предложением/попыткой. Невидимое в фоне предложение не считается показанным. Если пользователь просто свернул приложение, нельзя автоматически записать отказ.
- Для подсказки фиксировать, была ли целевая стрелка снята ручным нажатием или естественным автоснятием. Эти исходы не смешивать в «игрок последовал подсказке».
- Для шага каскада отдельно считать ручные удаления, естественное автоснятие отмеченных стрелок и бонусные удаления A2. Один ручной tap с пятью последствиями не равен шести пользовательским действиям.
- Получение живого Hint, начало его reveal, начало анимации и фактическое использование — разные события. Дубликат receipt/повторный restore не создаёт нового смыслового grant или consumption. Использовать стабильный ID события/операции для дедупликации при анализе; exactly-once доставку в кабинет не обещать. После commit возможны неполная доставка или повтор транспорта, их покрытие отражается отдельно. Новый аналитический outbox/service для этого пакета не требуется.
- У маршрута отдельны право на весь маршрут, продвижение по нему и завершение. Шаги не превращаются в отдельные rewarded conversions.
- У продолжения считать первый успешный ручной ход, долю завершений, повторную потерю жизней и выход до полезного действия. Автоматическая анимация возврата жизней не является полезным действием игрока.
- У события loss не закрывать всю попытку, если она может продолжиться. Финальный outcome — завершение, подтверждённый restart/abandon или другой явно определённый конец. Фон сам по себе не равен окончательному отказу.
- Оставить ограниченный транспорт. Не отправлять отдельный аналитический вызов на каждый кадр/блик/частицу. При перегрузе регистрировать число потерянных событий; не скрывать неполноту данных. Если ключевой join теряется, коммерческий вывод по такому набору данных ограничен.

## C.5. Деньги и проверяемый источник дохода

В текущем `onAdImpression` денежный `ImpressionData` не используется; собственного `reportAdRevenue` нет, Gradle исключает `analytics-ad-revenue` [C3, C6]. Это не доказывает отсутствие денег в рекламном кабинете: состояние автоматической интеграции с AppMetrica не установлено.

1. Установить, какой один денежный источник будет каноническим для сравнения вариантов: настроенная интеграция/выгрузка либо корректная передача ILRD. Записать источник, покрытие форматов, валюту и способ связи с назначением варианта.
2. Если нужна ручная передача, использовать реальные данные SDK impression callback; проверить поддержку и конфигурацию версии 8.6.0, а также необходимый AppMetrica revenue module. Не обновлять весь SDK/runtime без отдельной причины. Официальные ILRD-данные включают revenue/currency и precision; precision нельзя терять [C7].
3. Каждый monetary факт привязывается к фактическому impression/session и варианту. Preload, request, show invocation и earned не являются денежными показами. Отсутствующее значение помечается как unknown, а не как ноль.
4. Проверить отсутствие двойного учёта при автоматическом и ручном маршрутах. Если получить единый надёжный join невозможно, прямо ограничить коммерческую интерпретацию; не подменять её умножением ad requests на предполагаемый eCPM.
5. Денежные отчёты SDK могут содержать оценку. Их не называть окончательными выплатами. Валюты нормализуются явным способом; значения разных валют нельзя просто складывать.
6. Получить контрольный путь exact APK → реальное устройство → события/денежная выгрузка. Записать commit, versionCode, APK SHA-256, профиль устройства, режим рекламы/аналитики и фактические найденные записи. Успешный plugin call, `accepted: true`, локальный тест или GIF не доказывают доставку в кабинет.

Основной результат сравнения: суммарный рекламный доход на все назначенные подходящие установки за одинаковое созревшее семидневное окно. В знаменателе остаются пользователи, не нажавшие Hint, не посмотревшие рекламу и рано ушедшие. Нельзя сравнивать только зрителей ролика или смешивать полное семидневное окно одной группы с неполным окном другой. Доступность денежной выгрузки и покрытие impressions сообщать рядом с результатом.

Дополнительно: D1/D7 возвращаемость, прохождения/выходы, доход по форматам и placement, частота использования помощи, ожидание рекламы, повторная потеря жизней после continue. Улучшение отдельной конверсии не принимается за доказательство роста общего дохода. До запуска определить критерий выбора и разумную длительность/объём по фактическому трафику; не выдумывать универсальный порог uplift или статистическую мощность без данных.

## C.6. Включение, сборки и отдельный эксперимент частоты

- Сначала проверить базовую измеримость и целостность помощи. Затем один продуктовый кандидат. Назначение варианта стабильно для установки, его версия сохраняется в событиях и earned описаниях. Принудительные QA-переключатели доступны только в изолированном тестовом режиме.
- Общие исправления корректности могут быть включены для всех. Новый автокаскад, ручной маршрут и bundle продолжения не смешиваются в одном изменении коммерческих условий. В каждый момент должно быть ясно, какую гипотезу проверяет вариант.
- Для пользователя выдать подписанную совместимую `.playtest` APK с отдельным прогрессом, test ads и выключенной аналитикой. Проверить фактические значения внутри APK и сертификат обновления. Не предлагать удаление реальной игры ради установки.
- Для доставки аналитики нужен отдельный изолированный QA-профиль с отдельным debug AppMetrica приложением/ключом и соответствующим тестовым окружением. Не включать production analytics в пользовательскую `.playtest` ради проверки данных. Эмулятор/браузерные double-тесты не заменяют проверку физического SDK и кабинета.
- При отсутствии доступа к устройству/кабинету завершить кодовые проверки, подготовить APK и явно отметить оставшийся внешний gate. Не заявлять готовый live A/B или доказанный финансовый эффект. Публикация в RuStore и включение live эксперимента — отдельные действия за пределами подготовки тестовой поставки.
- Поздний отдельный эксперимент CADENCE-LAB может сравнить короткий backoff после failed/no-fill/cancel до показа с полноценной паузой после реально показанного fullscreen. В первой поставке сохраняются исходные 150 активных секунд, две новые победы, начальная защита и явный Next. Одновременно менять их и failure policy нельзя. Preload никогда не расходует cadence.


Критерии C-01...C-18 находятся в `ACCEPTANCE.md`. Редкая коллизия составной награды A4 описана в TASK.md, раздел 4.2.
