# Стрелки 0.23.0 — независимый аудит измерения и неудач

Дата: 13 ноября 2026, Екатеринбург. Проверенный исходник: `794bef1e5056800f2dd42343b02fe5f8fb1b586c`; последняя прикладная версия 0.23.0 / Android code35. Read-only snapshot: `/workspace/scratch/e5bf09a1dcbf/arrows-commercial-audit-20261113`.

## Вывод

Новая основа измерения уже реализована. Есть отдельные факты предложения, принятого запроса, SDK-сессии и impression, earned, сохранения/резерва/получения права, reveal и фактического применения; после продолжения есть первый ручной успешный ход, повторный loss, выход, restart и завершение. Денежные данные теперь читаются из SDK callback и соединяются с назначением варианта. Повторять прежнее ТЗ как будто этого нет неправильно.

Подтверждён один конкретный дефект событийной воронки: **явный Restart после видимого предложения помощи не фиксируется как выбор относительно этого предложения**. Ещё есть ограничение наблюдаемости потерь транспорта и неоднозначное обозначение тестового аналитического окружения. Эти пункты разумно закрыть до сравнения коммерческих вариантов.

Текущая игра после неудач сохраняет фиксированное поле, историю ошибок и принятые правила. По проверенным путям нет персональной подмены следующего уровня на основании нескольких проигрышей. Это соответствует действующим решениям, а не обнаруженный дефект. Новый глобальный DDA/director сейчас не обоснован.

## 1. Подтверждённый дефект: потерянный выбор Restart

**Приоритет:** P1 для измерения/готовности эксперимента; не блокирует обычную игру и не теряет игровое право.

### Фактическое воспроизведение

| Сценарий UI | Предложение до действия | Итоговые события | `assistance_choice` |
|---|---|---|---|
| Hint виден → Restart → подтверждение | Есть `assistance_offer` | Есть `level_restart` и `attempt_final(outcome=restart)` | **Отсутствует** |
| Rewarded continue виден при0жизней → Restart → подтверждение | Есть `assistance_offer` | Есть `level_restart` и `attempt_final(outcome=restart)` | **Отсутствует** |
| Hint виден → прямой Home | Есть `assistance_offer` | Есть `level_exit` | Есть `choice=exit` |
| Hint виден → нажать Hint | Есть `assistance_offer` | Принят request | Есть `choice=accept` |

Все четыре сценария завершились без page errors. Это не предположение только по внутреннему unit-вызову: использованы настоящие кнопки текущего UI, существующая очередь сохранений и настоящие отправители событий.

### Причина

- `src/game/helpOffers.ts:22–27`: `visible(false)` немедленно удаляет текущий `episode`.
- `src/game/surface.ts:199–203,428`: открытие диалога Restart устанавливает modal/dialog blocker.
- `src/game/surface.ts:319–322,460–465`: следующий sync перестаёт считать Hint/lives offer видимым и вызывает `visible(false)`.
- Только после подтверждения `src/game/surface.ts:223` вызывает `helpOffers.choice('restart')`.
- `src/game/helpOffers.ts:36`: без `episode` вызов ничего не отправляет.

Требование уже было в выданном пакете: `docs/iterations/assistance-2026-11-13/MEASUREMENT.md:90` требует явный tap/отказ/выход/Restart относительно соответствующего offer. Общий `attempt_final=restart` не сохраняет непосредственную связь с конкретным эпизодом предложения.

### Минимальная доработка

При открытии подтверждения Restart сохранить ограниченный контекст исходного предложения/эпизода. После подтверждённого успешного restart отправить один связанный выбор; при отмене подтверждения не отправлять restart. Смена попытки, новое независимое предложение и обычный уход в фон не должны получить устаревшую привязку. Не считать фон отказом. Не менять игровое сохранение/экономику ради этого события.

Приёмка: два воспроизведённых UI-пути дают по одному связанному выбору; Cancel не даёт выбора restart; многократный sync/два tap не дублируют событие; direct Home/accept продолжают работать.

Evidence:

- `measurement/reproduce-offer-choices.mjs`
- `measurement/offer-choice-results.json`

Команда из папки отчёта: `node measurement/reproduce-offer-choices.mjs /path/to/arrows`. Скрипт проверяет указанный HEAD, использует зависимости/готовый dist этого checkout, сам поднимает временный preview4197 и закрывает его; исходник не меняет. Предварительно нужны `npm ci`, `npm run build` и установленный Playwright Chromium. Результат сохраняется рядом со скриптом. Аналогично запускается `node measurement/reproduce-transport-loss.mjs /path/to/arrows`; он не требует браузера/dist.

## 2. Наблюдаемость потерь и окружения — небольшой пакет перед коммерческим запуском

### 2.1. Потери событий считаются, но не доходят до анализа

`src/platform/analytics.ts:20–34` ограничивает число незавершённых вызовов32 и увеличивает локальные `dropped`/`failed`. `snapshot()` возвращает счётчики, однако поиском по `src` не найден ни один их потребитель; тесты читают snapshot, приложение — нет. В JSON-контракте нет health/coverage события. Счётчики не сохраняются и после пересоздания транспорта обнуляются.

Контролируемое воспроизведение:33 валидных события при32 задержанных bridge promises →32 попадания в bridge,1drop. После разрешения promises и flush диагностического события нет; новое создание analytics имеет dropped0. Это доказывает ограничение наблюдаемости, **не доказывает**, что реальная игра часто перегружает transport.

Требование C.4 уже просило сообщать число потерянных событий и ограничивать выводы при потерянных joins. `revenueCohorts` видит некоторые orphan impressions, но не может узнать о полностью потерянном `ad_impression_value`, если никакой health/coverage сигнал не пришёл.

Минимально: редкий агрегированный health snapshot с причинами drop/failure и контекстом аналитического окружения; отчёт покрытия сравнивает SDK impression events, денежные наблюдения и успешные joins. Не новый per-event durable outbox и не сбор геометрии/сырых сохранений. При нулевой доставке самого health события полноту всё равно нельзя обещать — нужен контроль кабинета/экспорта.

Evidence: `measurement/reproduce-transport-loss.mjs`, `measurement/transport-loss-results.json`.

### 2.2. `qa` сейчас означает `.playtest`, а не все тестовые данные

- `ArrowsAdsPlugin.java:67`: `playtest=true` только для applicationId с `.playtest` и `AD_MODE=test`.
- `native/android/arrows-platform.gradle:4–8`: обычная debug/test сборка может использовать demo ads и `APPMETRICA_DEBUG_API_KEY`, при этом её package не `.playtest`.
- `src/game/helpOffers.ts:14,63`: аналитический `qa` берётся именно из `rewardedState.playtest`.
- `tools/assistance-revenue.mjs:6,15`: фильтрация тестовых назначений/сессий доверяет `qa`.

Следовательно, обычная analytics-enabled test сборка получит `qa=false`. Отдельный debug AppMetrica проект организационно изолирует данные; текущая выгрузка сама не доказывает, что строка пришла из live окружения. Это **не доказательство загрязнённого production кабинета** — таких данных аудит не получал.

Перед отдельным QA/device/export gate следует передавать явное окружение build/ad/analytics и проверять его на входе денежного анализа. `.playtest` оставить без аналитики. Тестовые скалярные ILRD нельзя принимать за оплаченные показы по одному лишь `qa=false`.

Семантические ограничения для анализа:

- `continue_outcome` закрывает наблюдение этого продолжения на явном Home/exit; если игрок позже вернётся и закончит поле, outcome этого continue уже не становится completed. Это не финальное закрытие попытки. Для метрики «когда-либо завершил ту же попытку» нужно соединять с `attempt_final`, а не считать только continue rows.
- Для обычного Hint есть применение и общий итог attempt, но нет отдельного события первого самостоятельного успешного хода **после использования Hint**. Все последующие обычные успешные ходы сейчас в аналитику не отправляются. Поэтому вопрос «после подсказки сделал ещё хотя бы один самостоятельный ход?» по нынешнему custom contract напрямую не измеряется. Можно добавить один ограниченный milestone на entitlement, если это действительно выбранная гипотеза; логировать каждый tap не нужно.
- `level_error` не содержит arrow ID; по агрегатам доступны жизнь/first и attempt, но нельзя восстанавливать геометрию ошибки. Это разумное ограничение; ошибка touch/знания правил/поиска различается отдельным наблюдением, а не догадкой по одному счётчику.
- Доставка событий best effort: durable игровой факт не гарантирует доставленного analytic fact, и её exactly-once не обещают.
- В событиях нет собственного session ID; для анализа сессий/retention потребуется реально доступная сессия и identity из AppMetrica export либо явная зафиксированная аналитическая дефиниция. Наличие native SDK само по себе не доказывает готовый отчёт D1/D7 по вариантам.

## 4. Реакция на неудачи: фактическое поведение

- `domain/board.ts:61–78`: первая ошибка по конкретной стрелке отнимает жизнь, повторная по ней — нет. Ошибочная стрелка сохраняется и автоматически уходит после фактического освобождения; это полезный механизм восстановления уже существует.
- `save.ts:293–302`: Restart создаёт новую попытку **того же сохранённого level**, а не подбирает более лёгкую геометрию. Неиспользованная earned помощь проходит reserve.
- `save.ts:311–315`: одна lifetime free continuation возвращает3жизни; последующие права живут в существующем rewarded пути.
- `helpLedger.ts:139–156`: обычное продолжение возвращает3жизни. A4 может дополнительно дать полезный A1/сохранить существующий help, но это отдельный изолированный вариант, не текущая универсальная реакция после нескольких неудач.
- `save.ts:305–309`: после победы следующий фиксированный campaign index. Выбор не читает число fail/retry/help как вход difficulty.
- `helpOffers.ts:69–82` и `freshHelpLedger`: обычное значение `single-v2`; A2/A3/A4 доступны через изолированные playtest controls, влияют на будущие attempts. B1 отдельная лаборатория, не live экономика.
- Действующие решения фиксируют campaign/daily/trophy/content identities. Автоматический reroll или снижение сложности текущего опубликованного поля нарушили бы этот контракт.

## 5. Рекомендация

**Ближайшее небольшое изменение:** закрыть подтверждённый Restart choice и собрать проверяемое покрытие/окружение аналитики в существующем C-контуре. После этого пройти отдельный exact APK → устройство → debug analytics/export контроль. Последнее остаётся внешней приёмкой; браузерный repro и исходник её не заменяют.

**Следующая продуктовая гипотеза, если нужен тест:** измерить один самостоятельный ход/новое застревание после помощи и сравнить уже готовый A1 с одним из существующих кандидатов. Новые поля, DDA, экономика, дополнительные рекламные места для этого не нужны.

KIT IMPACT: NONE для этого аудита. Найденные пункты находятся в локальном игровом wiring/analytics. Никакой подтверждённый баг существующего kit API не установлен.
