## Основной вывод

Связка «попросил rewarded → отложить interstitial» уже реализована. Вводить её заново не требуется. Обнаружен один воспроизводимый пробел в правдивом отображении рекламной готовности: после окончания 30-секундного backoff интерфейс может продолжать говорить «Попробуйте позже». Это небольшая правка существующего модуля C, а не основание вводить новый рекламный режим или повышать частоту.

150 секунд — ограничение следующего **interstitial**, а не глобальный запрет на повторный добровольный rewarded. Это различие важно в итоговом описании.

## Фактическая последовательность

### Старт и первая реклама

`src/progression/adCadence.ts:1–16` хранит `activeMs`, `nextRequestMs`, `progressAtRequest`.

- Пока `wins < 6`, interstitial запрещён.
- После шестой уникальной победы он уже может стать допустимым, если выполнены остальные условия. Формулировка «первые шесть побед полностью свободны от показа после них» была бы неточной: порог именно `wins >= 6`.
- Требуются 150 накопленных допустимых активных секунд и минимум две новые уникальные победы с последнего расходования возможности.
- Кампания и daily участвуют в одном счётчике (`save.ts:279–284`). Повторная победа на уже зачтённой дате/задаче не создаёт новую уникальную победу.

Показ можно запросить только через явный Next после свежей победы. Startup/Back/меню/восстановленный result не инициируют его (`surface.ts:184–197`). Финал c120 дополнительно обходит возможность показа. Если игрок вышел в Home, автоматический вход в следующую задачу через `enterCampaign` не становится рекламной точкой (`surface.ts:122–127`). Это действующее продуктово-техническое правило, не обнаруженный дефект.

### Что считается временем

`surface.ts:49–58` использует `performance.now()`, ограничивает один шаг учёта максимумом 1000 мс и считает только открытое незавершённое игровое поле с жизнями, без блокеров и переходов. Обязательный tutorial исключается из `pendingAdTime`. Меню, фон, потеря всех жизней, SDK fullscreen и ожидание рекламы не приближают interstitial. Это время присутствия на подходящем поле, а не исключительно время жестов: размышление на открытом поле тоже считается.

Накопление сохраняется вместе с попыткой (`save.ts:273–276`), а не вычисляется по настенным часам. При старом save без adCadence выдаётся новая пауза от текущего числа wins (`adCadence.ts:3–5`).

### Rewarded и следующая межуровневая реклама

`requestReward` фиксирует descriptor до SDK show (`surface.ts:163–182`). В той же долговечной операции `prepareHelpRequest` вызывает `deferAds` (`save.ts:368–380`). Следующий interstitial становится доступен не раньше чем ещё через 150 активных секунд и две новые уникальные победы.

Отложенный межуровневый показ после помощи уже решён более консервативно, чем просто пауза от закрытия видео. Здесь пауза начинается от подготовленного запроса; показ необязателен. No-fill, отмена и отказ SDK тоже могут отложить interstitial.

Это прямо соответствует старому ТЗ: `MEASUREMENT.md:19,134`, `ACCEPTANCE.md:C-17`. Менять сейчас такой расход возможности на «только после настоящего impression» означало бы начать отложенный CADENCE-LAB. Такая перемена не является исправлением неправильного выполнения ТЗ.

### Interstitial preload и отказ

Прогрев начинается при `confirmedWins >= 4` и `activeMs >= 120000`; запрос к native не чаще раза в 30 секунд (`surface.ts:460–465`). Native не держит больше одного объекта и одного загрузочного запроса; на load failure/timeout — 30-секундная пауза, таймаут загрузки 15 секунд (`ArrowsAdsPlugin.java:122–130`).

Перед реальным запросом возможность атомарно потребляется в `ProgressStore.consumeInterstitial`; это происходит до SDK результата (`surface.ts:189–195`, `save.ts:280–285`). Если готового объекта нет, native немедленно завершает запрос как unavailable (`ArrowsAdsPlugin.java:143–150`). Нет ожидания загрузки interstitial поверх перехода. Следующая возможность снова требует исходные 150 секунд/две победы.

Неудачный write не расходует подтверждённую возможность. Соответствующая проверка уже есть в `tests/unit/adFlow.test.ts:42–46`.

### Возврат после рекламы и новой сессии

`createAdTransition` ждёт одновременно terminal SDK outcome и снятие всех независимых foreground-блокеров; смена уровня принимается один раз (`src/platform/adTransition.ts:4–29`). Контролируемые tests покрывают оба порядка dismiss/resume и отсутствие выдуманного завершения по таймауту (`tests/unit/adFlow.test.ts:49–64`).

Отдельной новой паузы для каждого холодного запуска/долгого отсутствия нет. Если перед выходом сохранены накопленное время и необходимые победы, после возвращения следующий **новый** win + Next может быть eligible. Простой restore уже завершённого result по-прежнему не покажет рекламу.

Это факт действующей политики, не доказательство плохого удержания и не нарушение имеющегося ТЗ. Добавлять returnee grace сейчас преждевременно без наблюдаемого раннего ухода/частоты таких случаев.

## Подтверждённая находка ADS-01

**Приоритет: P1 — правдивая готовность после ошибки.**

### Воспроизведение

Файл `ads-readiness-probe.mjs` напрямую импортирует актуальные `createAds` и `adCadence`, использует контролируемый native bridge и монотонные часы. Не заменяет реализацию адаптера; не запускает Android SDK.

Команда:

```bash
node ads-readiness-probe.mjs /path/to/arrows
```

Результат сохранён в `ADS_READINESS_PROBE.json`:

1. При сохраняющемся спросе запускается один preload.
2. Приходит load_error с `phase=backoff`, `retryInMs=30000`.
3. Монотонное время переходит на 30001 мс, повторный `setRewardedDemand(true)` ничего не делает.
4. Адаптер возвращает `retryInMs=0`, но `phase=backoff`.
5. До явного refresh был всего один prepare и один начальный status.
6. `refreshReadiness()` возвращает актуальный `idle`.

### Причина и последствие

- Native `RewardedCacheState.phase(now)` переводит backoff в idle по истечении `retryAt` (`RewardedCacheState.java:9–12`).
- JS getter уменьшает только `retryInMs`; переход фазы предусмотрен для ready→expired, но не backoff→idle (`ads.ts:117`).
- `setRewardedDemand` не повторяет RPC, если булев спрос не изменился (`ads.ts:119`).
- `refreshReadiness` вызывается при создании адаптера и после show, без обработки истечения backoff на остающемся открытым поле (`ads.ts:63,113,164`).
- Hint выбирает надпись «Попробуйте позже» по `phase=backoff` (`surface.ts:297–299`). Кнопка остаётся доступной (`surface.ts:305`), поэтому это **не вечная блокировка SDK или кнопки**, а неверная подсказка о возможности повторной попытки.

Вероятное продуктовое последствие: часть игроков может не попробовать ещё раз, хотя повторная попытка уже разрешена. Величина этого эффекта и потеря дохода не измерены.

### Ограниченное исправление

После окончания backoff при ещё актуальном foreground-спросе однократно получить/применить новый статус либо снять устаревшую формулировку на нейтральное «Проверим видео». Явный tap должен оставаться нормальным путём повторной попытки. Не показывать ready без объекта, не заводить бесконечный retry и не расходовать ad cadence от обновления статуса.

Приёмка: непрерывно открытое поле, preload error→30 с→текст и диагностика больше не утверждают действующий запрет; tap запускает ровно одну разрешённую попытку. Уход в фон отменяет плановый refresh/загрузку; старое поколение не переписывает более свежую готовность.

Связь со старым ТЗ: `MEASUREMENT C.2`, существующие `C-02/C-06`, дополнение edge case к `C-03`. Тест `rewardedReadiness.test.ts` уже проверяет TTL expiry и coalescing, но не эту границу backoff. Не нужно пересматривать остальные готовые C-пункты автоматически.

## Что не следует сейчас объявлять новым необходимым scope

1. **Общий defer interstitial после rewarded** — уже есть. Проверка актуального кода снимает эту гипотезу до реализации.
2. **Уменьшить паузу после no-fill** — отдельный CADENCE-LAB, уже записанный в отложенных задачах; потенциальный выигрыш в доступных показах не равен росту прибыли/удержания.
3. **Добавить session/day caps или returnee grace** — возможная продуктовая проверка по реальным сессиям, сейчас нет доказанной необходимости и согласованного численного порога.
4. **Автоматически показывать чаще после сложного уровня/ошибок** — отсутствует и не предлагается; проблема помощи и проблема рекламной частоты должны проверяться отдельно.
5. **Копировать Meowdoku cooldown по странам/возрасту установки** — собственные данные не подтверждают такой перенос.

## Playtest, обычная сборка и деньги

`native/android/arrows-platform.gradle:3–17` принудительно задаёт test ads и пустую аналитику для `.playtest`. Обычный debug по умолчанию тоже test; отдельный debug analytics key опционален. Release gate требует deliberate live mode и все live SDK значения (`:29–34`), а playtest release запрещён.

`ArrowsAdsPlugin.java:47–49` при пустом analytics key отключает и автоматическую рекламную аналитику SDK. Это не отсутствие готового монетизационного кода, а заявленная изоляция тестового APK.

По документации текущей поставки точный `.playtest` 0.23.0/code35 проверен на package/config/payload/signature, но физическая установка, SDK fill/earned/background и отдельная аналитическая QA-сессия остаются NOT RUN (`docs/evidence/assistance-023/ACCEPTANCE.md:47–50,60,74`). В данном аудите эти внешние заявления не переименовываются в независимое Android-доказательство.
