# Стрелки: контекстный акцент A1 после первой ошибки

Дата: 14 ноября 2026. Статус: готовая постановка следующего изолированного QA-кандидата. Сам кандидат ещё не реализован.

## 1. База и результат задачи

Проверенный main: `56f65a4ee5b9b169b1a53ab21f06e186b9619d48`.
Код приложения: `f8a75b3106f8194d1ad27a2a58ede7c3b30d48d3`.
Версия: **0.25.0 / Android code 37**. Runtime kit: `a9325265e87583a4872cf6a158e1e881a0d7508e`; guidance: `e04a3fe87ca93d506e01df4acc5afe690408cefa`.

Перед реализацией сверь фактическую рабочую ветку: более свежие изменения сохраняются. Прочитай актуальные AGENTS, HANDOFF, PROJECT_DECISIONS, UI_POLISH_025 и действующие assistance-контракты. По Task Router достаточно UI motion и измерения экспериментов. Наличие более свежего guidance не означает наличие новых API в установленном runtime.

U1-U6 уже исправлены. A1-A4, M1, flawless и банк V4 уже существуют. В этой итерации добавить только один кандидат: после первой реальной ошибки ненадолго выделить уже доступную кнопку A1. Гипотеза - игрок лучше замечает помощь в момент затруднения. Польза и коммерческий эффект ещё не измерены.

На выходе: совместимая `.playtest` APK с прежним сертификатом, более высоким versionCode, тестовой рекламой и выключенной аналитикой; кандидат по умолчанию выключен. Нужны выбор контроль/акцент в существующей изолированной QA-поверхности, реальные сравнительные записи и краткий отчёт по ACCEPTANCE.md. Проверки телефона, реального SDK и кабинета AppMetrica не блокируют подготовку APK; они остаются отдельной стадией.

## 2. Варианты и область действия

- `off`: текущий интерфейс без новой cue-логики и новых trace-записей.
- `control`: вычисляет тот же подходящий момент и локально фиксирует opportunity, но ничего не рисует.
- `cue`: те же условия плюс один декоративный акцент.

Это принудительные QA-варианты, не случайный live A/B-тест. Cue mode - отдельная QA-настройка; не добавлять off/control/cue в HelpVariant, setNextHelpVariant или assistance-v1. Существующие назначения силы помощи и их identity сохраняются.

Использовать существующую изолированную QA-поверхность. Выбор действует только для новой попытки и не переключает вариант текущей, в том числе после reload до её первой ошибки. Для этого достаточно маленьких QA-метаданных режима по attempt ID вне канонического save/earned-контракта. Старой активной попытке без такой записи назначить off; новый выбор применяется после обычного создания следующей попытки/Restart. Метаданные не должны расти без ограничения или изменять реальные saves. Не строить новый экспериментальный сервис. Production остаётся без кандидата; существующие QA/test transport не попадают в production payload.

Работает только обычный вариант помощи A1 с фактическим эффектом `single-v2` и источником `advertisement`. Другие назначенные варианты A2/A3/A4, включая их fallback, B1/control, активная помощь, старые legacy-права и резервная уже заработанная помощь не входят в эту проверку. Для них сохраняется обычный UI.

## 3. Подходящий момент

Нужны одновременно следующие условия:

1. Текущее изменение действительно принято авторитетным writer: обычный ручной `move`, результат `error`, `first=true`, а каноническая история ошибок этой попытки после принятия содержит **ровно одну** ошибку.
2. `first=true` сам по себе недостаточен: это первая ошибка по данной стрелке. Сердца также не заменяют историю ошибок, поскольку могут восстанавливаться.
3. До этого действия Hint уже была видна, разрешена и закончила обычное появление. Прежнее правило трёх активных секунд сохраняется. Если кнопка впервые показалась вследствие sample()/sync() того же действия или её появление ещё идёт, cue пропускается.
4. Сохранён текущий владелец attempt/content, обычная игра активна, нет модалки, туториала, перехода, запроса рекламы, активной/резервной помощи или другой presentation, с которой акцент будет конкурировать. Хранилище подтверждено и доступно.
5. Текущий A1-оффер подходит по пункту 2; **свежий** `platform.ads.rewardedState.phase === 'ready'`. Не использовать сохранённый старый snapshot ready: getter уже учитывает expiry.

Состояние UI следует фиксировать до takeTime()/sample() и постановки progress.move(), отдельно от post-change sync, иначе на границе трёх секунд одновременно запустятся обычное появление и новый cue. Это снимок только возможности будущего сигнала; авторитетная ошибка всё равно подтверждается после принятия move. Не менять существующий Hint-таймер ради этой проверки.

Сначала зафиксировать opportunity одинаково в control/cue. Далее можно дождаться окончания текущего отклика ошибки, но не ждать будущей загрузки рекламы или будущего появления Hint. Перед первым показанным кадром повторно проверить владельца и условия. Если момент устарел, акцент отменяется, opportunity остаётся в trace.

Доменные факты берутся из принятого изменения состояния. `impact` - только событие представления; оно не заменяет принятие ошибки. Звуки/движение сердца должны закончиться естественно; cue не задерживает следующий ввод и не вызывает новую ошибку.

## 4. Внешний вид и владение

Один мягкий контур внутри уже существующей кнопки Hint. Её текст, video-mark, readiness, размеры и положение остаются видны.

- Отдельный небольшой декоративный span/i: `aria-hidden`, `pointer-events:none`, абсолютный inset, существующий radius, border-box. Контур рисовать внутрь, без сдвига layout.
- Для начального QA-варианта: **1200 мс**, появление opacity 200 мс, удержание 500 мс, затухание 500 мс. Это стартовая настройка проверки, не исследовательски доказанный универсальный тайминг.
- Reduced motion: неподвижный opacity-only акцент 400 мс. Никакого scale, движения или бесконечной пульсации.
- Сохранять текущие токены и контраст; не осветлять заливку под текстом.
- Новая подпись, звук, вибрация, движение камеры и подсветка поля в V1 не добавляются. Сравнивается один визуальный сигнал.

Нельзя целиком переиспользовать `hintReady()`: его 900-мс вход начинает с opacity 0 и изменяет transform настоящей кнопки. Нельзя брать `notice()/presentation()` как готовый cue: они скрывают anchor или отменяют текущий arrival. Нельзя делить временный `ui-press-feedback` между press и cue: у press собственное удаление слоя.

Достаточен отдельный маленький handle внутри существующего finite-motion manager. Он владеет только своим слоем и animation, штатно завершается через finish/destroy. Обновление runtime или перенос нового OwnedDomMotion не нужен.

## 5. Отмена, повторы и сохранения

До показа и во время cue новое успешное действие, следующая ошибка/смена логического состояния поля, получение/применение помощи, нажатие Hint, изменение readiness, меню/модалка, рестарт, фон, resize, смена языка и teardown отменяют акцент. Его удаление не отменяет press, обычное действие, рекламу, arrival или сохранение.

Один подходящий момент на попытку. При повторной ошибке по прежней стрелке, второй новой ошибке и восстановлении старой попытки cue не возникает. Возврат из фона не повторяет его. Если условия не подошли при первой ошибке, последующая готовность рекламы не создаёт новый повод.

Отдельное долговечное `cueSeen` обычно не нужно: история ошибок уже каноническая, load не является новым move. Если устройство writer может повторно публиковать тот же live-change, использовать ограниченный idempotency-key текущей попытки в QA-слое. Не менять схему save и восстановление earned-прав только ради косметики.

Точный корень/маршрут до earned не раскрывается. Не менять геометрию, сердца, силу A1, бонусы, продолжение, рекламные интервалы, правила выдачи, SDK и кит.

## 6. Измерение без включения AppMetrica

Для V1 достаточно **двух локальных QA-записей**:

- `opportunity`: первый подходящий момент до treatment; одинаковое определение в control/cue.
- `shown`: факт реально начавшегося видимого акцента, не вызов функции и не окончание анимации.

Обе записи связываются через устойчивые identity текущей попытки и cue-version. К существующему offer episode привязать, если он уже есть, без создания/перевыдачи права. В trace хранить QA-вариант, attempt/content/mode, active-time, фактический A1-эффект/source, readiness и причины отмены при необходимости. Не выгружать полную геометрию или save.

Существующий `assistance-v1` - назначение типа помощи, а не назначение интерфейсного cue. Не переименовывать его и не считать случайным распределением control/cue. Для тестовых сценариев использовать отдельный локальный trace через изолированный harness/QA-режим. AppMetrica остаётся OFF; production и Android analytics schema ради QA не расширять.

Первое сравнение использует текущие `level_complete`, `level_exit`, `level_restart` и рекламную воронку по связанным попыткам. Пропуск исхода остаётся unknown. M1 - дополнительная диагностика только среди получивших помощь.

Общего события первого обычного успешного хода после любой ошибки сейчас нет. Для этой первой реализации не добавлять второй универсальный observer. Метрику «первый самостоятельный ход среди всех подходящих» оставить будущим отдельным изменением, если она понадобится. Не выдавать M1 за такое покрытие.

Для будущего live-теста отдельно понадобятся стабильное назначение до воздействия, связная выгрузка, достаточный baseline и денежные данные. В знаменатель должны входить все подходящие назначенные игроки, включая случаи отмены cue до paint и непользователей помощи. Forced QA, рост кликов и test-реклама не подтверждают доход.

## 7. Проверка и доставка

Сначала воспроизвести актуальную базу и полезные случаи из EVIDENCE.md; не повторять весь старый аудит. Проверить ACCEPTANCE.md на новой реализации, `npm run check`, подходящие browser regression. При изменении native-контракта - соответствующие sync/JVM; .playtest собирать по существующему проверенному пути.

На записи показать одинаковый подготовленный участок и действие в control/cue. Отдельно показать отмену быстрым правильным ходом и сохранение нажатия у края Hint. Записи делать из настоящего собранного приложения; указать source/build, подготовленный прогресс и controlled SDK transport, если он использовался. Не рисовать эффект отдельно поверх видео. Существующие звуки не менять; физический feel и native SDK не объявлять проверенными из браузера.

Передать APK с прежним сертификатом и более высоким кодом, файл с хешем/версией, 2-3 короткие настоящие записи и таблицу PASS/FAIL/NOT RUN. Готовность кабинета/реальных денег не является условием выдачи этой тестовой APK. Production-включение и публикация в стор не входят в пакет.

KIT IMPACT: ожидается REUSE существующих seams. Механизм и политика cue остаются локальными для «Стрелок»; перенос в общий кит требует отдельной реальной повторяемости, а не сходства названий.
